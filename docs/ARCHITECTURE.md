# BG Media — архитектура

## 1. Цель и границы

BG Media — самостоятельный кроссплатформенный мультимедийный движок. Первый этап
реализует музыкальный анализ и синхронизацию хореографии; его можно использовать
без BeyGram, без сети и без конкретного UI.

Текущий результат этапа:

- `bgmedia_core` — независимая C++20-библиотека: анализ PCM, карта ударов,
  басовые акценты, тишина, кеш, модель времени, расчёт хореографии.
- `bgmedia_miniaudio` — адаптер декодирования WAV/MP3/FLAC.
- `apps/desktop` — тестовое SDL3-приложение: декодирует через miniaudio, играет
  через miniaudio, но сам движок об этих зависимостях не знает.
- `tools` — headless-анализ, генератор синтетических треков, benchmark.

Видеоплеер, сервер, Telegram-интеграция и 3D-модель в этот этап намеренно не
входят. Точки расширения под них описаны в разделе 8.

## 2. Направление зависимостей

```text
apps/desktop (SDL3 + miniaudio playback + UI)
   │
   ├── bgmedia_miniaudio (только decoder adapter)
   └── bgmedia_core
         ├── audio      : PcmBuffer, WAV decoder, decoder interfaces
         ├── analysis   : STFT, onset, tempo, beats, bass, silence, sections
         ├── cache      : versioned binary analysis cache
         ├── sync       : TransportSnapshot + PlaybackClock
         ├── choreography: DanceCue + CharacterPose, media-time sampling
         └── render     : ICharacterPresenter (no SDL types)
```

Правила:

1. `bgmedia_core` не включает SDL, miniaudio, JNI, Android, iOS и не открывает
   аудиоустройство.
2. KissFFT скомпилирован внутри core как object library; наружу FFT-зависимость
   не протекает.
3. Декодирование и воспроизведение — разные роли. `IAudioDecoder` отдаёт PCM;
   `IPlaybackController` принимает команды play/pause/seek/rate и отдаёт
   `TransportSnapshot`. Плеер может быть miniaudio, AAudio, AVFoundation или
   тестовый fake.
4. Анализ не зависит от FPS. Хореография сэмплируется по media time.
5. `apps/desktop` — единственное место, где есть окно, мышь, файловый диалог и
   звуковая карта.

## 3. Модульные имена на будущее

Концептуальные модули не создают лишних библиотек сейчас, но архитектура уже
разделена по их ответственности:

| Модуль | Назначение | Текущее состояние |
|---|---|---|
| **BG Audio** | декодирование, аудиовыход, микширование | decode adapter; воспроизведение в host-приложении |
| **BG Video** | видео-треки и синхронизация кадров | не реализовано (точки расширения есть) |
| **BG Beat** | BPM, удары, onset, бас, тишина | `bgmedia_core/analysis` |
| **BG Motion** | хореография, cues, позы | `bgmedia_core/choreography` |
| **BG Sync** | общая модель времени, latency, seek, rate | `bgmedia_core/sync` |
| **BG Effects** | эффекты поверх медиа | интерфейсы появятся вместе с видеослоем |

Новые модули должны подключаться как отдельные CMake-таргеты/адаптеры, не меняя
публичные типы анализа. Например, BG Video сможет использовать тот же
`TransportSnapshot` и `PlaybackClock`, не затрагивая `Analyzer`.

## 4. Модель времени

Единая аннотация: **`BGMEDIA_TIME_SECONDS`** — секунды в таймлайне исходного
медиа. Это не wall clock, не кадры и не семплы.

`TransportSnapshot` содержит:

- `sourcePosition` — позиция следующего исходного семпла/кадра, который плеер
  будет рендерить;
- `duration`;
- `playing`;
- `rate`;
- `outputLatency` — уже отрендеренный объём, который ещё не дошёл до колонок;
- `discontinuity` — счётчик seek/stop/loop-событий;
- `hostTime` — монотонное время хоста.

`PlaybackClock`:

1. вычитает latency с учётом rate;
2. экстраполирует позицию между нерегулярными callback-снапшотами;
3. плавно исправляет мелкий jitter и не даёт курсору идти назад во время
   воспроизведения;
4. делает snap при seek, смене rate, смене play/pause и большом расхождении.

Это модель, пригодная и для будущего видео: видео-кадр выбирается по
presentation timestamp относительно той же audible media time, а не по FPS.

## 5. Анализ

### 5.1 Вход

`AudioData` (interleaved float) → `PcmBuffer` (mono + fingerprint). Анализ
принимает только `PcmBuffer`, поэтому не знает ни путь, ни формат, ни плеер.
Источник может быть WAV, MP3, FLAC, а на Android — MediaCodec.

### 5.2 STFT и спектральные признаки

- Hann window; по умолчанию 2048 samples / hop 512 при 44.1–48 кГц
  (auto: 512/1024/2048 для низких/средних/высоких sample rate).
- 80 mel-подобных лог-полос; 48 полос для компактного spectrogram.
- Spectral flux по лог-энергиям, low-band flux (< 180 Гц), RMS.
- Onset envelope: вычитание локальной медианы, мягкое сглаживание,
  нормализация по 98-му перцентилю. Отдельно хранится sharp-envelope для
  точного времени пиков.
- Для tempo используется pulse envelope с акцентом на низкие частоты:
  `max(lowEnv, 0.35 * fullEnv)`. Это не даёт хай-хэтам «удвоить» BPM, но
  оставляет рабочим материал без баса.

### 5.3 Темп и метрический уровень

1. Autocorrelation broadband onset/pulse envelope.
2. Кандидаты BPM из локальных максимумов плюс семейство уровней:
   `1/3, 1/2, 2/3, 3/4, 1, 4/3, 3/2, 2, 3`. Это важно для 12/8, half-time
   и offbeat-материала; прежняя модель генерировала только 2:1.
3. Для кандидата ищется фаза и считается:
   - precision попаданий предсказанных ударов в onsets с поправкой на
     случайное совпадение (density normalization),
   - on/off контраст,
   - low-band pulse evidence: hit rate и контраст по отфильтрованному
     `lowEnergyRatio` низкочастотному envelopes,
   - autocorrelation поддержка.
   Старые coverage/onset-hit-rate не входят в выбор уровня: они монотонно
   растут с плотностью сетки и были основной причиной выбора tatum вместо
   пульса.
4. Кандидат-субгармоника получает поддержку, только если у более медленного
   родительского уровня есть не меньшая low-band pulse evidence. Это не
   жёсткая фиксация BPM: уровни оцениваются по музыкальной энергии.
5. `bpmConfidence` — эвристическая оценка периодичности/BPM, не вероятность.
   Для уровня есть отдельный `bpmLevelConfidence`; альтернативы остаются в
   `bpmCandidates`. `octaveAmbiguous` теперь означает любую метрическую
   неоднозначность (2:1, 3:1, 3:2, 4:3), а UI пишет `METRIC AMBIGUOUS`, не
   `STABLE`.

Для темпа с изменением:

- локальные окна 6 с с шагом 1.5 с;
- стабильные сегменты выделяются только при согласии нескольких окон;
- между ними создаётся `TempoTransition` с пониженной уверенностью;
- `tempoStable=false`, и UI не показывает переход как «достоверный BPM».

`result.bpm` при смене темпа — удобное агрегированное число для сортировки/логов.
Оно **не** является утверждением, что весь трек имеет этот темп; источник
истины — `tempoSegments` + `tempoTransitions`.

### 5.4 Beat tracking

- Ellis-style dynamic programming по **beat evidence**:
  broadband onset envelope + отфильтрованный low-frequency pulse;
- локальный период берётся из tempo-структуры (может меняться);
- анализ идёт по непрерывным не-тихим областям, поэтому в длинной тишине удары
  не выдумываются;
- удары, найденные DP, привязываются к ближайшему onset-пику в пределах ~55 мс;
- phase rescue применяется только когда текущая сетка почти не имеет low-band
  поддержки (`basePulse < 0.15`), иначе сильный syncopated bass мог бы увести
  beat на offbeat;
- слабые доли, продолженные сеткой без прямого onset, помечаются
  `extrapolated=true` и имеют низкую confidence;
- meter/downbeat: grid index накапливается по фактическому времени и локальному
  периоду, а не по индексу вектора; один пропущенный удар больше не сдвигает
  все следующие такты. Фаза оценивается по low-band pulse/energy, first-beat
  используется как слабый tie-break; `meterConfidence`/`downbeatConfidence`
  честно низкие при равномерном пульсе;
- timestamps onset/beat используют середину нового аудиоинтервала STFT-кадра,
  а не центр окна: это устраняет систематическое опережение примерно на
  13–14 мс;
- на каждом ударе есть `beatInBar`, `barIndex`, `downbeat`, `strength`,
  `confidence`.

### 5.5 Басовые акценты

Басовый акцент — не «громкий всплеск». Кандидат принимается, если:

- пик low-envelope;
- доля **линейной энергии** ниже ~180 Гц достаточно велика;
- есть ненулевой low-band spectral flux;
- пик не находится в тишине.

Broadband swell (шум/тарелки) даёт высокую общую громкость, но малую долю
низкочастотной энергии и отбрасывается. Причины решения сохраняются в
`lowBandRatio`, `strength`, `confidence`, `nearestBeat`, `offsetFromBeat`.
Несколько басовых нот между ударами могут попасть в карту — это реальные
низкочастотные события, а не ложные срабатывания по громкости.
`nearestBeat` выставляется только при попадании в local-period окно
(не более 28% IBI); offbeat-бас остаётся событием с `nearestBeat=-1` и не
превращается в BassDip в choreography.

### 5.6 Тишина и секции

- RMS threshold относительно 95-го перцентиля (по умолчанию −42 dB);
- регионы короче 0.8 с не репортятся;
- удары и басовые акценты в тишине не создаются;
- `activeRatio` используется в confidence;
- секции — консервативная energy novelty эвристика; уверенность низкая и не
  выдаётся за структурный анализ.

## 6. Кеш

- Ключ: `contentHash(PCM) + config.fingerprint()`, в который входит
  `kAnalyzerVersion`.
- Формат: magic `BGMedia1`, версии формата/схемы/анализатора, размеры,
  payload + checksum. `kAnalyzerVersion=2`, schema/cache format `2` после
  изменения метрической семантики BG Beat; старые записи должны стать miss.
- Payload хранит раздельные `bpmConfidence`, `bpmLevelConfidence`,
  `beatPhaseConfidence`, `downbeatConfidence`.
- Запись атомарная: temp-файл → rename.
- Загрузка проверяет магию, версии, ключи, checksum, диапазоны времени,
  размеры массивов. Битый файл — `Corrupt`, а не падение и не частичный
  результат.
- Кеш не содержит путей, поэтому перемещение/переименование файла не мешает
  попаданию (при совпадении PCM).
- Кеш не является публичным форматом обмена; для Android/JNI лучше
  сериализовать события в JSON/flatbuffer, а не читать `.bgm` напрямую.

## 7. BG Motion 2.0 и рендеринг

`ChoreographyBuilder` — чистая функция от `AnalysisResult`. В версии 2.0 он
строит не только legacy-cues, но и непрерывный `MotionKeyframe` timeline
([docs/MOTION.md](MOTION.md)):

- ключи на под-битовой сетке, точных ударах, границах бара, anticipation и
  release-окнах;
- кроссфейд базовых движений до границы бара;
- `AccentTarget` для каждого beat с позой, которая достигается в точный
  музыкальный момент;
- freeze в тишине и плавный fade к нему;
- шесть движений: Bounce, Sway, ArmWave, HeadNod, BassDip, AccentPose;
- `ChoreographySampler::sample(choreography, mediaSeconds)` интерполирует
  соседние keyframes (кубический Hermite или выбранный easing) и возвращает
  расширенный `CharacterPose`;
- `sampleStepped()` сохранён для сравнения со старым ступенчатым поведением;
- `sampleWithDebug()` отдаёт индексы keyframes, blend, easing и phase для
  debug-панели.

`CharacterPose` остаётся backend-independent: старые поля сохранены, добавлены
суставы головы/коленей/локтей, chest twist, hip shift и rotation с
shortest-arc интерполяцией. `ICharacterPresenter` — интерфейс для SDL-демо,
спрайтов, Live2D, glTF, Telegram-аватара и т.д. Engine не содержит типов
графического API.

SDL-демо рисует робота из примитивов, но это лишь один presenter. Ноги решаются
двухзвенной IK с закреплёнными стопами, поэтому bob/dip не вызывают скольжения.
Замена рендерера не требует изменений в анализе или хореографии.

### Гарантия акцента в удар

1. Builder вычисляет `AccentTarget.pose` в точное время beat.
2. В этот же момент добавляется `MotionKeyframe` с тем же результатом.
3. Sampler при совпадении media time с ключом (1e-6 с) возвращает позу ключа
   напрямую, без размытия интерполяцией.
4. Accent overlay имеет weight 1 ровно в beat time (подготовка 0→1, затем
   короткий hold и release 1→0).
5. `tests/test_motion.cpp` проверяет каждый `AccentTarget` с порогом 2e-4.

Anticipation начинается до удара, целевая поза достигается на ударе,
follow-through/инерция продолжаются после него.

## 8. Точки расширения под BG Video / BG Effects

Сейчас видео не реализовано. Чтобы добавить его без переписывания ядра:

1. **Общий clock.** `TransportSnapshot` + `PlaybackClock` уже отделяют
   audible media time от источника и FPS. Видео будет использовать тот же
   clock (audio-master) и выбирать кадр по PTS.
2. **Видео-декодер как адаптер.** Добавить `video/IVideoDecoder`, который
   отдаёт кадры с `presentationTimeSeconds`, по аналогии с
   `audio/IAudioDecoder`. Ядро анализа не меняется.
3. **Video track / compositor.** `BG Video` сможет владеть списком
   видео-треков, каждый со своим offset/clock mapping. Общая модель времени
   останется одна; при необходимости добавится `MediaTimeline` с
   track offsets, но `TransportSnapshot` уже содержит нужные поля.
4. **Effects.** BG Effects подключается как цепочка presenter/compositor
   поверх готового кадра; он не должен влиять на анализ.
5. **Синхронизация.** Аудио — master clock. Видео выбирает ближайший кадр не
   позже audible времени; при отставании — drop, при опережении — hold.
   `PlaybackClock` уже умеет latency/rate/seek.
6. **Сборка.** `bgmedia_video` будет отдельным CMake-таргетом, который
   линкуется только теми приложениями, которым нужен видео. Core и тесты
   останутся без SDL/FFmpeg/MediaCodec.
7. **Кеш.** Анализ и видео-индексы будут разными артефактами с независимыми
   версиями. Это позволит обновлять анализ без инвалидации видео-кеша.

## 9. Потоки и производительность

- `Analyzer` — immutable и thread-safe для параллельных вызовов.
- UI запускает декодирование + анализ в отдельном `std::thread`; прогресс
  передаётся через атомарные значения и mutex-protected stage.
- GUI не блокируется во время анализа; можно отменить загрузку/начать новую.
- Кэш проверяется до анализа.
- Анализ не привязан к FPS; экран может рендериться 30/60/144 Гц, а
  хореография останется в media time.
- Измерения: `docs/MEASUREMENTS.md`.

## 10. Ошибки и честность результатов

- Ошибки декодирования/анализа возвращаются как `AnalysisReport`/`DecodeResult`,
  а не молчаливые пустые данные.
- Кеш: `Hit / Miss / Corrupt / Error`.
- BPM: confidence + альтернативы + octave flag.
- Смена темпа: stable segment vs uncertain transition.
- Beat: `extrapolated` и confidence.
- Meter/downbeat: confidence, низкая на неоднозначном материале.
- Секции: низкая confidence.
- UI показывает «MIXED / CHANGE SUSPECTED», а не фиктивный стабильный BPM.

## 11. Ограничения текущего этапа

- Моно-даунмикс; стерео-панорама не анализируется.
- Темп-приор 120 BPM может ошибаться на экзотических темпах; альтернативы
  доступны, `preferredBpm` настраивается.
- Размер такта оценивается эвристически (2/3/4), фаза downbeat может быть
  неоднозначной на равномерном пульсе.
- Изменение темпа всегда показывается как возможное, а не доказанное.
- Скорость воспроизведения в демо — линейный resampler (меняется питч), не
  time-stretch.
- Latency оценивается по периодам устройства; в UI есть sync trim ±150 мс.
- Нет Android/iOS сборки, видео, эффектов и Telegram-интеграции.
- In-memory decoder ограничен 1 GiB; для очень длинных файлов нужен стриминговый
  анализ (следующий этап).
